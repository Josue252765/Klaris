-# Reglas de Codex para Klaris

## Marcas de agua y estilo
- CERO marcas de agua de IA (prohibido "# Generated by", "Created with AI", "Co-authored-by", etc.) en código, comentarios, commits o docstrings.
- Sin comentarios redundantes ni explicaciones dentro del código Python; el código se explica solo.
- Código Python 3.8+ limpio, usando Decimal para montos (nunca float), typing y dataclasses donde aplique.
- Mensajes de commit en español neutro, imperativo, sin marcas de IA.

## Antes de escribir código: verificar, nunca asumir
- ANTES de importar cualquier clase, función o símbolo, verifica que existe con el nombre exacto:
  `grep -n "^class\|^def" <archivo>` en el módulo de origen. No asumas nombres por convención o por cómo "deberían" llamarse.
- Si necesitas usar algo de core/ventas.py, core/producto.py, core/inventario.py, etc., lee el archivo real primero, no un resumen ni un doc desactualizado.
- Si un nombre en la documentación (docs/modulos/*.md) no coincide con el código real, el código real manda — pero avisa la discrepancia en tu reporte, no la corrijas en silencio.
- Nunca inventes un nombre de clase/función "razonable" para que el import compile. Un ImportError es preferible a un nombre incorrecto que compila por casualidad.

## Arquitectura no negociable
- core/ es lógica pura sin I/O; repositorios inyectados por constructor.
- IDs con str(uuid4()).
- Sin funcionalidad fuera del MVP actual (nada de empleados/auth/SQLite/reportes extra sin pedirlo explícitamente).
- Función/método ≤30 líneas, archivo ≤300 líneas. Si un archivo va a superar el límite, divide en paquete por dominio como ya se hizo con cli/acciones/ y persistence/repositorios/.
- Avisa antes de reinterpretar la spec si una tarea la contradice; no decidas solo.

## Tests
- Antes de reportar "listo", corre `python -m pytest -q` y pega la salida COMPLETA (no resumas "todo pasa" sin mostrarla).
- El número de tests que deben pasar es "todos los existentes + los nuevos que agregues", nunca un número fijo — verifica con el conteo real de la corrida, no con un número de una sesión anterior.
- No dejes tests rotos ni comentados/skippeados para "arreglar después".
- Si agregas un test nuevo que importa algo de otro módulo, verifica el nombre real en ese módulo (ver sección anterior) antes de escribir el import.

## Flujo de entrega
- No hagas commit tú mismo salvo que se te pida explícitamente.
- Reporta siempre: qué archivos tocaste, resultado completo de pytest, y cualquier discrepancia encontrada entre docs y código real.
- Si algo no se pudo verificar (ej. no pudiste correr un comando), dilo — no reportes como hecho algo que no confirmaste.
